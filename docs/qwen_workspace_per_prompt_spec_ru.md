# Спецификация: Qwen Workspace с ограничениями на один prompt

**Статус:** согласованный дизайн, ожидает реализации

## Problem Statement

Текущий Qwen Workspace запускает один длительно живущий интерактивный Qwen
процесс и передаёт в него последующие сообщения через `--input-file`. Поэтому
ограничения `--max-session-turns`, `--max-tool-calls` и `--max-wall-time`
исчерпываются общей сессией процесса. При длительном разговоре следующий
prompt перестаёт выполняться после достижения лимита, хотя пользователю нужен
новый независимый бюджет для каждого отправленного prompt при сохранении общей
истории разговора.

Дополнительно текущий tray содержит отдельное окно `Qwen input...`, которым
пользователь не пользуется. Старые пункты запуска Qwen Workspace должны
остаться как безопасный fallback, а новый режим должен быть включён отдельными
пунктами, чтобы его можно было сравнивать и постепенно оптимизировать.

## Solution

Добавить новый режим Qwen Workspace на основе протокола `stream-json`.
Workspace запускает один Qwen-процесс с параметрами модели и лимитов, затем
передаёт каждый пользовательский prompt как отдельное сообщение протокола.
Qwen сбрасывает run-level бюджеты в начале каждого сообщения, а контекст
разговора остаётся общей сессией.

Новый режим запускается из tray отдельными пунктами, отличными от старых
`Qwen workspace...` и `Qwen workspace (--continue)`. Старые пункты и их текущий
механизм не изменяются.

В новом режиме верхняя часть окна является управляемой областью вывода
Qwen-событий, а нижняя часть сохраняет поле ввода, коррекцию Stepler и кнопку
отправки. Отдельное окно `Qwen input...` и его tray-пункт удаляются; поле ввода
внутри Workspace остаётся.

## User Stories

1. Как пользователь Qwen Workspace, я хочу запускать новый режим без prompt,
   чтобы сначала получить готовую сессию, а затем вводить сообщения.
2. Как пользователь, я хочу, чтобы для каждого нового prompt заново начинался
   лимит числа ходов модели.
3. Как пользователь, я хочу, чтобы лимит tool calls начинался заново для
   каждого prompt.
4. Как пользователь, я хочу, чтобы ограничение wall-clock time относилось к
   обработке одного prompt, а не ко всему времени открытого Workspace.
5. Как пользователь, я хочу сохранять общий контекст разговора между prompt,
   несмотря на сброс бюджетов.
6. Как пользователь, я хочу отправлять следующий prompt после того, как
   предыдущий достиг одного из лимитов, без ручного закрытия Workspace.
7. Как пользователь, я хочу видеть в Workspace ответ Qwen и понятный статус
   обработки prompt.
8. Как пользователь, я хочу видеть отдельное состояние для обычного ответа,
   достижения лимита, ошибки транспорта и остановки процесса.
9. Как пользователь, я хочу, чтобы prompt-ы отправлялись последовательно и не
   смешивались при быстрых нажатиях на кнопку отправки.
10. Как пользователь, я хочу запускать новый режим в выбранном рабочем
    каталоге.
11. Как пользователь, я хочу продолжать последнюю историю проекта через
    отдельный вариант нового Workspace с `--continue`.
12. Как пользователь, я хочу редактировать параметры запуска нового Qwen
    режима в настройках tray.
13. Как пользователь, я хочу получить предсказуемые параметры по умолчанию:
    модель `qwen38-flash-next`, 16 ходов, 30 tool calls, 20 минут и глубина
    subagent `1`.
14. Как пользователь, я хочу менять пользовательские параметры запуска без
    редактирования исходного кода или PowerShell wrapper-а.
15. Как пользователь, я хочу, чтобы транспортные параметры `stream-json`,
    необходимые для работы нового режима, нельзя было случайно сломать через
    обычный редактор настроек.
16. Как пользователь, я хочу сохранить старый пункт `Qwen workspace...` на
    случай несовместимости нового режима.
17. Как пользователь, я хочу сохранить старый пункт `Qwen workspace
    (--continue)` и его поведение.
18. Как пользователь, я хочу различать старый и новый режимы по названиям
    tray-пунктов.
19. Как пользователь, я хочу, чтобы перезапуск старого режима не зависел от
    реализации нового stream-json транспорта.
20. Как пользователь, я хочу, чтобы неиспользуемое отдельное окно `Qwen
    input...` отсутствовало в tray.
21. Как пользователь нового Workspace, я хочу сохранить ввод, коррекцию P/CP
    и отправку текста из нижней панели.
22. Как пользователь, я хочу, чтобы сбой отдельного prompt не завершал всю
    сессию, если Qwen-процесс продолжает работать.
23. Как сопровождающий, я хочу диагностировать запуск, отправку, ответ,
    ограничение и остановку без записи исходного prompt в лог.
24. Как сопровождающий, я хочу тестировать per-prompt поведение через границу
    транспорта, не полагаясь на ручные клики в WinForms.
25. Как сопровождающий, я хочу обновить release smoke checklist так, чтобы он
    отдельно проверял старый fallback, новый режим и отсутствие Qwen Input.

## Implementation Decisions

- Главный тестируемый seam — транспорт Qwen-сессии внутри нового режима
  Workspace. Он владеет запуском процесса, stream-json stdin/stdout,
  сериализацией prompt-ов, чтением событий, статусами и завершением процесса.
  WinForms UI только отображает состояние и передаёт текст этому seam.
- Новый транспорт использует один долгоживущий Qwen-процесс и отдельное
  stream-json сообщение для каждого prompt. Локальный Qwen CLI версии 0.24.0
  уже поддерживает `--input-format stream-json`.
- При запуске нового режима prompt не передаётся через `-p`. Первый prompt
  появляется только после ввода пользователем и нажатия отправки.
- Транспортные параметры stream-json и выбранный формат событий принадлежат
  Workspace и не редактируются пользовательским полем запуска.
- Пользовательские параметры запуска сохраняются в настройках tray как
  редактируемая коллекция аргументов, а не как PowerShell-команда. Меняются
  модель, бюджетные параметры и разрешённые дополнительные Qwen-параметры;
  protocol-owned параметры остаются под контролем Workspace.
- Значения по умолчанию для нового режима: модель `qwen38-flash-next`,
  `--max-session-turns 16`, `--max-tool-calls 30`, `--max-wall-time 20m` и
  `--max-subagent-depth 1`.
- `--continue` является выбором режима запуска, а не пользовательским prompt и
  не редактируется в поле аргументов. В новом режиме он восстанавливает
  последнюю историю проекта при старте процесса.
- После достижения лимита конкретного prompt транспорт возвращается в
  состояние готовности к следующему prompt, если Qwen остаётся доступным.
  Если процесс завершён самим Qwen или аварийно остановлен, Workspace
  показывает терминальный статус и не делает скрытый повторный запуск.
- Новые tray-пункты получают отдельные временные названия
  `Qwen workspace (per-prompt)...` и `Qwen workspace (per-prompt, --continue)`.
  Названия и порядок пунктов можно оптимизировать позже отдельной задачей.
- Старые `Qwen workspace...` и `Qwen workspace (--continue)` сохраняются с
  текущим механизмом, текущим embedded-terminal поведением и текущими
  ограничениями.
- Удаляется только tray-поверхность отдельного Qwen Input: пункт меню и
  специализированное окно. Общий контроллер коррекции и нижняя панель ввода
  нового Workspace не удаляются.
- Настройки с пустыми, несовместимыми или некорректно токенизированными
  аргументами не должны запускать новый режим. Пользователь получает ошибку
  в UI, а последняя валидная конфигурация остаётся сохранённой.
- Оригинальный текст prompt не записывается в диагностические логи. Логи
  могут содержать тип события, статус, длительность, exit code и счётчики.

## Testing Decisions

- Основные тесты должны проверять внешнее поведение транспорта: один запуск
  процесса, отдельные сообщения prompt, сохранение порядка, выдачу событий,
  сброс per-prompt бюджетов и возможность следующего сообщения после лимита.
  Тесты не должны проверять конкретную расстановку WinForms controls.
- Для transport-тестов использовать детерминированный локальный process fixture
  или другой реальный protocol boundary, который принимает stream-json и
  выдаёт контролируемые события. Не подменять весь транспорт mock-объектом.
- Отдельно проверить старт без `-p`, передачу модели/лимитов, режим
  `--continue`, ошибку malformed output, ранний exit и отсутствие prompt в
  логе.
- Настройки тестируются через сохранение, загрузку, значения по умолчанию,
  пользовательское изменение и отказ от невалидной конфигурации.
- Tray smoke-тест проверяет наличие двух старых и двух новых Workspace-пунктов,
  различие их аргументов, наличие пункта настроек и отсутствие `Qwen input...`.
- Workspace smoke-тест проверяет ввод, P/CP, отправку нескольких prompt,
  отображение ответа, достижение лимита одного prompt и успешную отправку
  следующего prompt.
- Release smoke должен последовательно проверить старый fallback, новый
  per-prompt режим, новый `--continue`, сохранение настроек и отсутствие
  отдельного Qwen Input.

## Out of Scope

- Удаление или переписывание старого Qwen Workspace и его двух tray-пунктов.
- Изменение самого Qwen CLI, его серверного режима, SDK или формата истории.
- Перенос старого Workspace на stream-json.
- Оптимизация финальных названий, группировки и порядка tray-пунктов.
- Изменение глобальных Qwen settings пользователя.
- Автоматический незаметный restart Qwen после завершения процесса.
- Передача prompt через `-p` в новом режиме.
- Полное удаление общего QwenInputCorrectionController, пока он используется
  новым Workspace.

## Further Notes

Официальная документация Qwen описывает для `stream-json` сброс бюджетных
счётчиков в начале каждого пользовательского сообщения и отличает его от
обычного single-run поведения. При несовместимости конкретной версии CLI
новый режим должен завершаться диагностируемой ошибкой, а старый Workspace
остаётся доступным как fallback.

Спецификация намеренно описывает новый режим как отдельную поверхность. Это
позволяет сначала подтвердить protocol и lifecycle на практике, а затем
оптимизировать tray UX без потери рабочего старого запуска.
